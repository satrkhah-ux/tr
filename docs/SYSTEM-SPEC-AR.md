## ٢. ما يفعله النظام

### المبيعات
- **مولّد البكجات** — معالج متعدد المراحل: العميل · الرحلة · المدن والليالي · الفنادق ·
  الطيران · المواصلات · الخدمات · التأشيرات · البرنامج اليومي · التسعير · المعاينة.
  كل مرحلة تُحفظ تلقائيًا، وقواعد تحقّق حاجبة تمنع إصدار عرض متناقض
  (مجموع ليالي المدن ≠ ليالي الرحلة مثلًا).
- **العروض الجاهزة** — كتالوج باقات الشركة، يُزامَن من Google Sheets ويبذر مسودة بضغطة.
- **إعادة تصميم بكج مورّد** — استيراد PDF أو صورة أو نص أو رابط، وقراءته آليًا
  (استخراج نصي + رؤية حاسوبية عند الحاجة) وإعادة إنتاجه بهوية الشركة.
- **محرّك تسعير** — سعر المورّد الصافي ← هامش ← سعر البيع، بقواعد هوامش وحدود دنيا
  وأسعار صرف. أسعار الشراء والأرباح **محجوبة بنيويًا** عن أي مخرج يصل العميل.
- **مستند العرض** — PDF بهوية الشركة، وصفحة عميل عامة بالرقم التسلسلي، ولقطة مجمّدة
  لكل إصدار فلا يتغيّر ما وُقّع عليه.

### العمليات (Operations)
- **مساران مستقلان لكل حالة**: مسار العميل (مؤكّد ← مسدّد ← مكتمل) ومسار التنفيذ
  (بانتظار الحجوزات ← محجوز ← فوتشرات ← جاهز للسفر). لا يُدمجان لأن العميل قد يسدّد
  بالكامل والفندق لم يُؤكَّد بعد.
- **سحب الحجوزات من العرض** — الفنادق والطيران والتأشيرات بتفاصيلها، فلا يُعاد إدخالها.
- **إسناد كل حجز** لقسم العمليات أو موظف أو **شركة متعاونة**، وتجهيز طلب الحجز
  ومراجعته قبل إرساله (واتساب عبر Chatwoot API أو نسخ يدوي)، مع سجل كامل لما أُرسل.
- **الفوتشرات** — فوتشر فنادق · تذكرة طيران · جدول سياحي · ملخص حجوزات، بهوية الشركة،
  بثلاث حالات مطبوعة: **حجز مبدئي** · **مؤكّد غير مُصدر** · **حجز كامل**.
- **رابط واحد للعميل** يعرض كل ما صدر ويحدّث نفسه.
- **بيانات الجوازات مشفّرة** AES-256-GCM، والجدول محجوب على مستوى قاعدة البيانات،
  وكل اطلاع يُسجَّل باسم من فتحه ووقته.

### الإدارة
- لوحة تنفيذية (مبيعات · أرباح · هوامش)، لوح كانبان، بيانات مرجعية (دول · مدن · فنادق ·
  مطارات · أنواع غرف · مواصلات)، أدوار وصلاحيات، سجل تدقيق، تطبيق ويب مثبَّت (PWA).

### تكاملات قائمة
- **Chatwoot / Teletel** — بحث جهات الاتصال وإرسال رسائل واتساب.
- **Telegram** — إشعارات فورية + Mini App لتسجيل دخول الموظفين.
- **Open-Meteo** — طقس البرنامج اليومي (تنبؤ أو معدّل مناخي، ومُعلَّم أيهما).
- **OpenAI** — صياغة نصوص البرنامج وقراءة ملفات الموردين (اختياري، خلف مفتاح).
- **طبقة موردي الفنادق** — واجهة موحّدة مع محوّل TBO Holidays جاهز (بانتظار بيانات الاعتماد).

## ٣. الربط — الوضع الحالي بصراحة

**لا توجد اليوم واجهة API عامة للشركاء.** هذه حقيقة تقنية يجب أن تصل للطرف الآخر
بوضوح قبل أن يبني على افتراض خاطئ.

ما هو موجود فعلًا:

| السطح | الحالة | صالح للربط؟ |
|---|---|---|
| Next.js **Server Actions** (٢٧ ملفًا) | كل منطق النظام | ❌ بروتوكول داخلي غير موثّق ولا يُستدعى من خارج التطبيق |
| `/api/telegram/*` (٣ مسارات) | webhook للبوت | ❌ خاص بتيليجرام |
| `/client-offer/[serial]/pdf` · `/voucher/[token]/pdf` | توليد مستندات | ⚠️ للقراءة فقط، ومحمي بالرقم التسلسلي أو برمز |
| **Supabase PostgREST** | مُولَّد تلقائيًا فوق الجداول | ⚠️ **لا يُعطى لطرف ثالث**: سياسات الوصول الحالية تمنح أي مستخدم مصادَق كل شيء |

### ما نقترحه للربط

**الخيار الأول — واجهة REST مخصّصة للشركاء (المُوصى به).**
مسارات تحت `/api/partner/v1/*` بمفتاح لكل شريك، وصلاحيات محدودة بالنطاق، وحدّ معدّل،
وسجل لكل استدعاء. الشكل المعتاد:

```
POST /api/partner/v1/offers          إنشاء عرض
GET  /api/partner/v1/offers/{serial} حالة عرض + رابط الـPDF
POST /api/partner/v1/bookings        طلب حجز
GET  /api/partner/v1/bookings/{id}   حالة الحجز + رقم التأكيد
POST /api/partner/v1/webhooks        تسجيل رابط لاستقبال تغيّر الحالة
```
مصادقة: `Authorization: Bearer <partner_key>` · استجابات JSON · أخطاء بأكواد HTTP قياسية.

**الخيار الثاني — Webhooks فقط.**
إن كان المطلوب أن يُخطَر الطرف الآخر بتأكيد حجز أو إصدار فوتشر دون أن يقرأ بياناتنا،
فهذا أبسط وأسرع وأقل خطرًا: نُرسل إليه، ولا يقرأ منّا.

**ما لا نفعله:** تسليم مفتاح Supabase لطرف ثالث. سياسات الوصول الحالية تمنح كل
مستخدم مصادَق قراءة كل الجداول، فمفتاح واحد يعني كشف قاعدة البيانات بالكامل.

## ٤. الأسئلة التي نحتاج إجابتها منهم

قبل تحديد الشكل والجهد المطلوب:

1. **الاتجاه** — هل يقرؤون منّا، أم يكتبون إلينا، أم الاثنان؟
2. **الكيانات** — عروض؟ حجوزات؟ عملاء؟ توافر وأسعار؟
3. **التزامن** — لحظي (webhook / استدعاء مباشر) أم مزامنة دورية؟
4. **الحجم المتوقع** — عدد الاستدعاءات في اليوم.
5. **من يستضيف** — هل لديهم واجهة نستدعيها نحن، أم يريدون استدعاء واجهتنا؟
6. **مواصفاتهم** — إن كانت لديهم وثيقة API جاهزة، فإرسالها يوفّر دورة كاملة.

## ٥. الأمن والامتثال — ما يُذكر في أي مراجعة تقنية

- **TypeScript strict** بلا `any`، وحواجز على مستوى الأنواع تمنع وصول بيانات الشراء
  والأرباح والجوازات إلى أي مخرج يراه العميل — الخطأ فيها يفشل البناء لا يظهر في الإنتاج.
- **Row-Level Security** مفعّل على كل الجداول؛ وجدولا الجوازات وخزنة اعتمادات الموردين
  محجوبان تمامًا حتى عن المستخدم المصادَق، والوصول إليهما عبر الخادم فقط وخلف صلاحية.
- **تشفير AES-256-GCM** لبيانات الجوازات واعتمادات الموردين، بمفتاح في بيئة الخادم.
- **سجل تدقيق** لكل إجراء حسّاس: من ومتى وماذا.
- **لا إجراء لا رجعة فيه يقع صامتًا** — كل حجز خارجي وكل رسالة صادرة تحتاج ضغطة إنسان،
  وتُسجَّل.
- **HTTPS** بشهادة سارية، وتخزين خاص للملفات الحسّاسة بروابط موقّعة قصيرة الأجل.
